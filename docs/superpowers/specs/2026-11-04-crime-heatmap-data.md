# Crime heatmap data design

## Goal

Replace the three hand-written demo hotspots and invented risk percentages with an aggregate layer derived from SafeHer's existing CrimeDataBD CSV. Keep the map honest about the dataset's approximate coordinates and limited coverage.

## Current behavior

- `/heatmap/` reads `data/chittagong_incidents.geojson` generated by `precompute/seed_incidents.py`.
- That script writes three hard-coded points and synthetic `weight` values.
- `MapContainer` renders those values as `Risk: N%`, although they are not calculated from the dataset or a validated risk model.
- The existing canonical CSV has approximate latitude/longitude records, no year or victim-gender field, and a CC BY-NC 4.0 license. Routing uses only records within 5 km of the Chattogram graph center.

## Proposed behavior

1. Read the existing `backend/data/crimedatabd.csv`; do not add another source or query individual incident descriptions.
2. Keep only finite coordinates within Bangladesh bounds and within 5 km of the configured Chattogram graph center.
3. Aggregate records into approximately 1 km grid cells before returning any map data. Do not expose individual incident points or descriptions.
4. Return a GeoJSON FeatureCollection with each cell's aggregate `record_count` and a `relative_density` value normalized against the most populated cell. Include metadata for source, total usable records, displayed cells, coverage radius, approximate grid size, and the missing year/gender fields.
5. Cache the parsed aggregate in-process; the API should work in Lite Mode without pandas, graph files, or Supabase.
6. Render the layer as relative reported-record density. Tooltips show the approximate count in a grid cell; no text should call it a risk probability, current danger score, or verified street-level safety measure.
7. Replace or retire the hard-coded seed generator, and update `build_all.py`, data notes, README landing copy, and map UI text so no old dummy hotspot or false-precision claim remains.

## Data contract

```text
FeatureCollection
  metadata:
    source: "CrimeDataBD v4"
    coverage: "within 5 km of Chattogram graph center"
    grid_size_km: approximately 1
    temporal_coverage: unavailable
    victim_gender_field: unavailable
  features[]:
    geometry: approximate grid-cell center point
    properties:
      record_count: integer
      relative_density: number from 0 to 1
```

## Safety constraints

- Preserve the existing CSV and its attribution/license; do not fetch or merge a new dataset.
- Aggregate before returning data so approximate input coordinates are not presented as exact street incidents.
- The displayed values describe counts in the source data only; they do not imply incidents are current, independently verified, female-victim-filtered, or predictive of personal safety.
- Do not run tests, builds, or precomputation unless the user asks for verification.

## Review checklist

- No demo coordinates or synthetic risk weights remain in the active heatmap path.
- Chattogram radius and Bangladesh bounds match the existing route-data scope.
- Empty/missing CSV returns an empty, well-formed feature collection.
- Frontend labels use record counts and relative density, not percentages of risk.
- Dataset provenance and limitations remain visible in the map and project docs.
